# Preparation workspace update — 25 October 2026

## Implemented

- Password verification rejects plaintext values and provider markers. Production requires a non-default signing secret of at least 32 characters. Provider sign-in uses a separate client. Unknown/removed application accounts fail authentication.
- All filing/document operations use the authenticated owner. Administrative taxonomy routes require the server-assigned admin role. Mapping review identity comes from the authenticated account. Durable revision history records actor, timestamp, resulting state and content digest; it is not a tamper-proof external audit service.
- Supabase failure never becomes memory-only success. Explicit `KVK_LOCAL_DATA_DIR` enables durable SQLite for local development only. Concurrent overlapping writes use optimistic versions. All mutations commit before success. Saved filings are selected explicitly by company, year and filing ID.
- Taxonomy extraction caches are separated by archive digest, serialized with an extraction lock, atomically installed and checked against extracted-file digests before reuse. Entry-point parsing runs on the background worker.
- English-first guide and reporting profiles retain Dutch terminology. The guide explains number formats, tagging, adoption, locking and delivery. Financial-year and adoption dates are no longer pre-filled with misleading defaults. Extraction warnings are visible. Technical tools are grouped separately. Modal focus trapping, Escape handling, keyboard focus styles and responsive layout support were added.
- Persistent “Not submitted to KVK” wording; local validation and package downloads do not claim filing success. Manual provider instructions are available in the guide. Export remains gated. Output packages have a conservative application size limit.
- API regression fixtures now use durable isolated storage and authenticated actors, with additional authentication, ownership, stale-write and release-cache tests.

## Required before cloud rollout

Apply `supabase_security_migration.sql` using an authorized database migration connection. It adds `filings.version`, a new owner-scoped source-document table, and restricts public table access. Back up first and test the migration in staging. Existing filings with no `created_by` remain inaccessible: an operator must verify and assign each rightful owner (lowercase login identifier), then copy the corresponding legacy source records as described in the migration. This update deliberately does not infer ownership or expose old filings to the next login.

Configure `JWT_SECRET_KEY`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and preferably `SUPABASE_ANON_KEY` for provider sign-in. Existing plaintext local passwords must be converted to supported PBKDF2 hashes or replaced through the normal account setup process. Roles are assigned in `digihub_users`; `LOCAL_USER_ROLES` is only for explicit local account configuration. Filings currently belong to individual accounts: organization/team sharing and a distinct authorized second reviewer require a future explicit membership model.

For local development, set `KVK_LOCAL_DATA_DIR` to a private directory and configure hashed local accounts, then run `bash app/start.sh`. Local mode is refused when `PROD=1` or `VERCEL` is set.
